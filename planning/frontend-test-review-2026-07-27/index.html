    Frontend Test Review, 2026-07-27¶

    Scope: frontend/ React app. Run in an isolated worktree (test/frontend-review) to avoid collisions with concurrent sessions. Assessed three things: do the tests pass, is coverage robust, and do the tests assert what a USER expects (not just what was built), including a11y and Playwright e2e.

    1. Test health (all green after one fix)¶

    Check Result
    npm run typecheck (tsc -b) PASS (exit 0)
    npm run lint (eslint, incl. all e2e tiers) PASS (exit 0)
    npm run test:coverage (Vitest, 125 files) PASS, thresholds met
    npm run test:e2e (mocked Playwright chromium, incl. a11y.spec.ts) 185 pass / 1 flake, fixed

    The one e2e failure (authoring-queue.spec.ts:52) was a latent strict-mode flake, not an app bug (zero code changed on the branch; passed 3/3 in isolation). getByText(request title) also matched the open dialog heading whose full text ("Build authoring plan: ") lives in the DOM while CSS-truncated. Under parallel load the React state flush that removes the row + unmounts the dialog lagged the mocked POST that <code>expect.poll</code> awaits, so both elements briefly coexisted. CI <code>retries: 1</code> masked it. Fixed by scoping the assertion to the row testid (unambiguous, and the true user-observable outcome). Verified 12/12 under 4x parallel-repeat stress. Committed <code>65de4ba</code>.</p> <p>Not run here (environment-gated, correctly local-only per project setup): <code>e2e-real/</code> (needs seeded local backend), <code>e2e-staging/</code>, <code>e2e-prod/</code>, <code>visual.spec.ts</code> (Linux-CI pixel baselines; deliberately ignored off-CI), and the design-system workspace (separate vitest + Codecov flag).</p> <h2 id="2-coverage-robustness">2. Coverage robustness<a class="headerlink" href="#2-coverage-robustness" title="Permanent link">¶</a></h2> <p>Vitest overall: <strong>Statements 95.93% | Branches 88.62% | Functions 94.97% | Lines 97.87%</strong>, well above the enforced <code>perFile: true</code> 70% floor. Weakest module is <code>src/api/readerApi.ts</code> (76% branches); <code>LandingPage.tsx</code> at 70% branches.</p> <p>Caveat that drove the rest of this review: line coverage measures execution, not assertion quality. High coverage here is real, but a handful of tests execute the line and then assert an implementation detail rather than a user outcome (below).</p> <h2 id="3-user-fidelity-verdict-by-surface">3. User-fidelity verdict by surface<a class="headerlink" href="#3-user-fidelity-verdict-by-surface" title="Permanent link">¶</a></h2> <p>Overall the suite is unusually faithful to user-observable behavior: e2e specs capture and assert real request bodies, the player Go-Back is proven by replay (not reversal) with fixtures a naive "undo" would fail, offline conflict is driven through real fake-IndexedDB, and auth fails closed (malformed <code>is_admin</code> stays false, <code>/me</code> rejection clears the bearer AND any child session).</p> <table> <thead> <tr> <th>Surface</th> <th>Verdict</th> </tr> </thead> <tbody> <tr> <td>Kid / Reader / Player / Offline</td> <td>Strong. Behavioral + adversarial. Minor CSS-class coupling.</td> </tr> <tr> <td>Guardian / Auth</td> <td>Strong. COPPA consent + shared-device boundary tested end-to-end.</td> </tr> <tr> <td>Admin (behavior)</td> <td>Strong. Real payload round-trips, fail-closed permission states.</td> </tr> <tr> <td>Hooks / client / infra</td> <td>Strong. Real interceptor logic, secret-leak assertions.</td> </tr> <tr> <td><strong>Accessibility</strong></td> <td><strong>Floor only.</strong> Real gaps (see below). Highest-value area.</td> </tr> </tbody> </table> <h2 id="4-prioritized-findings">4. Prioritized findings<a class="headerlink" href="#4-prioritized-findings" title="Permanent link">¶</a></h2> <p>The finding text below is the pre-fix baseline, recorded as it stood at the start of this review. Where a finding was closed later in this same PR, a <code>Status:</code> line says so directly under it; the original wording is left intact rather than rewritten, so the audit trail of what was wrong and what fixed it survives the merge.</p> <h3 id="p1-accessibility-is-a-happy-path-smoke-not-a-wcag-21-aa-floor">P1 - Accessibility is a happy-path smoke, not a WCAG 2.1 AA floor<a class="headerlink" href="#p1-accessibility-is-a-happy-path-smoke-not-a-wcag-21-aa-floor" title="Permanent link">¶</a></h3> <p>The a11y suite (axe + touch-targets) is well-built where it runs, but:</p> <ul> <li><strong>No keyboard-navigation coverage anywhere</strong>: no Tab/focus-order (2.4.3), no dialog focus-trap or Escape-to-close (2.1.2) assertions on any of the many dialogs (review approve/send-back/edit, assign-children, profile form). <code>review-edit.spec.ts:13</code> claims to drive "through the focus trap" but only clicks. Status: closed in this PR (commit 87600b1). <code>frontend/e2e/keyboard-nav.spec.ts</code> asserts focus-in, both-direction Tab-trap wrap, and Escape-restores-trigger on three representative <code>cyo-dialog</code> modals, plus keyboard reachability of the Send Back and Edit passage textareas. Writing it surfaced a real WCAG 2.1.1 defect: the shared Dialog focus-trap selector omitted <code>textarea</code>, locking keyboard-only admins out of both flows. Fixed in the same commit.</li> <li><strong>Admin pages scanned with EMPTY fixtures</strong> (<code>a11y.spec.ts:138-145,231-306</code>): severity pills, content-flag badges, valence badges, the exact colored status indicators where contrast/name-role-value issues hide, are never rendered under axe. Status: closed in this PR (commit 87600b1). Populated-fixture scans now cover the admin thresholds, dashboard, provider-allowlist, and review-queue surfaces.</li> <li><strong><code>/admin/review/:id</code> excluded from axe entirely</strong> (<code>a11y.spec.ts:15-17</code>), the richest admin page (flagged-passage cards, jump buttons, alerts, inline 422 errors). Status: closed in this PR (commit 87600b1). The exclusion rested on the page having no fixed heading to assert on, which an axe scan does not need; it is now scanned against a seeded review surface in both its flagged-passage and approve-failure-alert states.</li> <li><strong>Touch-target check is height-only</strong> (<code>admin-touch-targets.spec.ts:77-78</code>); WCAG 2.5.5 is 44x44. Also admin-scoped; kid reader choice buttons unverified. Status: closed in this PR (commit 87600b1). The admin sweep now asserts width as well, and <code>frontend/e2e/kid-touch-targets.spec.ts</code> measures every visible kid-reader choice button on both axes at a phone viewport.</li> <li><strong>Only resting render scanned</strong>; no open menus, error toasts, loading, 422 panels. Status: partially closed in this PR (commit 87600b1). Populated rows and the review detail's approve-failure alert are now scanned; open menus, toasts, and loading states still are not. This one stays open.</li> </ul> <h3 id="p2-half-built-two-device-conflict-resolution-product-decision-needed">P2 - Half-built two-device conflict resolution (product decision needed)<a class="headerlink" href="#p2-half-built-two-device-conflict-resolution-product-decision-needed" title="Permanent link">¶</a></h3> <p><code>resolveConflict(..., 'continue_from_this_device')</code> is unit-tested (<code>sync.test.ts:287-307</code>) but no component ever calls it or renders a choosing UI; every test asserts <code>conflict-dialog</code> is ABSENT. Reader only does silent newest-write-wins (<code>ReaderPage.tsx:321-327</code>). Either remove the dead branch + its test, or build+test the "ask the user" dialog. Right now the test implies a user flow that does not exist.</p> <h3 id="p3-small-high-value-untested-units">P3 - Small, high-value untested units<a class="headerlink" href="#p3-small-high-value-untested-units" title="Permanent link">¶</a></h3> <p>Status: closed in this PR (commit 65087ce). All four now have tests; see the per-item notes below.</p> <ul> <li><code>src/env.ts flagEnabled</code> has NO test, yet exists specifically to dodge the <code>Boolean("false") === true</code> trap. 3-line table test, high regression value. Closed by <code>frontend/src/env.test.ts</code>.</li> <li><code>src/reader/useReaderFontScale.ts</code>: no direct test that bumping text size actually enlarges the passage / persists across mounts (the child-observable payoff). Closed by <code>frontend/src/reader/useReaderFontScale.test.ts</code>, including the per-profile scoping of the storage key.</li> <li>Condition evaluator: add a metamorphic property (double-negation / De Morgan) to the fast-check layer, which today only asserts the return is boolean. Closed by three fast-check properties in <code>frontend/src/player/evaluator.test.ts</code>.</li> <li><code>useApi</code> 403 interceptor pass-through boundary (only 500 is asserted). Closed in <code>frontend/src/hooks/useApi.test.ts</code>.</li> </ul> <h3 id="p4-minor-implementation-coupling-nits-low-urgency">P4 - Minor implementation-coupling nits (low urgency)<a class="headerlink" href="#p4-minor-implementation-coupling-nits-low-urgency" title="Permanent link">¶</a></h3> <p>Status: partially closed in this PR (commit 65087ce). <code>ReaderChrome.test.tsx</code> and <code>LibraryPage.test.tsx</code> now assert observable behavior instead of class names. The rest were kept deliberately: they have no jsdom-observable alternative (jsdom applies no stylesheets, so a class is the only evidence the styling hook fired), and each is now annotated in place with that reasoning.</p> <p>CSS-class assertions used as proxies for observable state, each sitting beside a genuine assertion so not urgent: <code>Reader.test.tsx:367-388</code> (celebrate class), <code>ReaderChrome.test.tsx:81,97</code>, <code>KidShell.test.tsx:87,117-133</code> (data-attrs for theme/reduce-motion, no visible-effect assertion), <code>BudgetBanner.test.tsx:26,36</code>, various <code>toHaveClass('toast--*')</code>. Prefer role/label/<code>toHaveFocus()</code> over class tokens.</p> <h2 id="5-recommendation">5. Recommendation<a class="headerlink" href="#5-recommendation" title="Permanent link">¶</a></h2> <p>Status: acted on in this PR (commits 87600b1, 65087ce). The recommendation below is kept as written, as the reasoning that motivated the work; what it recommends was then done rather than deferred. What remains open after that pass is P2 (a product decision, not a test gap) and the non-resting a11y states (open menus, toasts, loading) noted under P1.</p> <p>Test health and coverage are in excellent shape; the flake is fixed. The one area that does not yet meet "tests what a user would expect" is <strong>accessibility for keyboard and assistive-tech users</strong> (P1). Recommend a focused a11y hardening pass (keyboard/focus-trap assertions on dialogs, populated + error-state axe scans, <code>/admin/review/:id</code> scan, 44x44 width on touch targets) as the
