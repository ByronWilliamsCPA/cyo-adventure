    Authoring Lessons Log¶

    Status: Accepted | Updated: 2026-07-25 Serves: A11 (structural quality tools across the corpus) Validated by: uv run python scripts/check_lessons_log.py

    Note on this first landing. The lessons below were learned building a three-book 16+ gamebook series (the Wyrmreach chain), and several Ref cells cite that series' spec, skeleton, and filled-story artifacts. Those artifacts are not part of this change: they land in a separate follow-up push so the process and tooling work can be reviewed on its own, alongside the other in-flight revisions to story development. Every lesson and every tooling change here stands without them; the story-dependent tests skip until they arrive (6 skips in the suite today), and the two Wyrmreach design and report documents are included because they are the evidence base each lesson cites.

    Every story development run appends here. The point is that a lesson learned once becomes a change to the tooling rather than folklore an author has to rediscover, so each row carries a proposed change and a status that tracks whether it landed.

    How to use this log¶

    When to append. At the end of any authoring run: a new story or series book, a skeleton promotion, a fill pass, or a validator/gate change made in service of authoring. If the run produced no lesson, append nothing; an empty run is a real outcome.

    What counts as a lesson. Something a future author or a future tooling change should act on. Three tests, any one of which qualifies it:

    1. It cost real iteration to discover (a rule interaction, a calibration, an ordering constraint).
    2. The tooling let a defect through, or reported it in a way that did not point at the cause.
    3. It would be re-learned from scratch by the next person, because nothing in the repo records it.

    A one-off typo is not a lesson. "The gate reports band membership, so the floor reads as a pass" is.

    Fields.

    Field Rule
    ID AL-NNN, sequential, never reused or renumbered.
    Date ISO date the lesson was recorded.
    Source The run that produced it (story slug, series book, or workstream).
    Category One of validator, tooling, authoring-craft, scale, metadata, process, docs, product.
    Lesson What is true, stated so it is actionable without reading the source run.
    Proposed change The change that would stop this recurring, or none (craft note) when the lesson is guidance rather than a code change.
    Status open, accepted, applied, rejected, or superseded.
    Ref Commit, PR, file, or doc. Required when status is applied, rejected, or superseded.

    Review cadence. Sweep the open rows whenever a phase is planned. An open row that has survived two phase boundaries is either genuinely low value (mark it rejected, with the reason in Ref) or it is real debt being avoided; either way, decide rather than let it sit.

    Status discipline. accepted means the change is agreed but unbuilt, and it must appear in a plan somewhere. applied means the change is merged and the Ref proves it. Nothing moves to applied on the strength of intent.

    AL-038 2026-07-25 adversarial review authoring-craft Narrowing a carried range erases reader outcomes, which qualifies AL-008. Verified from the specs: book 2 declares renown [0,5], book 3 declares [3,5], and startContinuation clamps carried ints into the receiving book's bounds, so every reader who finishes book 2 with renown 0, 1 or 2 arrives at book 3 indistinguishable from a maximum-reputation reader. My AL-008 justification ("a company that shut two doors cannot become unknown") was wrong on book 2's own terms. Two more in the same mechanism: book 2's deep_charts and oath_sworn are dropped without trace because book 3 does not declare them, and book 3 declares second_iron initial true while book 2 earns it from false, so a reader who finishes book 2 without it carries false and reads 746 nodes under a premise the prose contradicts. Author side DONE (renown widened to [0,5]); the rest is not author-fixable.     AL-058 2026-07-28 PR #449 review tooling SENTINEL_RE matches only well-formed {~SLOT:Word~} tokens, so it fails OPEN on a bisected one: truncating before stripping leaves {~HERO:Expl, which no later strip can ever match. The invariant is therefore strip-BEFORE-truncate ordering, not strip-presence, and ordering is invisible to any test whose fixture is shorter than the cut. PR #449 fixed this ordering in covers/prompt.py but left the identical shape unfixed in three sibling call sites (story_requests/anchoring.py, moderation/fidelity_review.py, flywheel/reguide_draft.py), two of which feed LLM prompts, so a fragment would have taught the next book's model that {~HERO:Expl is ordinary story text. Two changes. (1) When fixing an ordering bug, grep the repo for every other [:N] slice applied to blob-derived text rather than fixing the reported site alone. (2) Every regression test for this class must place the sentinel so the cut bisects it, AND assert that the pre-fix ordering leaked on the same input (assert "{~" in strip_sentinels(body[:N])), so the test fails loudly if a constant change later moves the cut and stops exercising the bug. applied tests/unit/test_anchoring.py::test_sentinel_straddling_the_title_cut_is_stripped_before_truncation, tests/unit/test_flywheel_reguide_draft.py::test_story_context_sentinel_is_stripped_before_the_600_char_cut, tests/unit/test_fidelity_review.py::test_sentinel_bearing_beats_and_body_never_reach_the_review_prompt
