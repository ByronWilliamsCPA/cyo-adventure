# Checker-repaired clean baselines for the plan reviewer (WP-3.7, D12)

Owner decision of 2026-11-22 (option 1): **checker-repaired baselines are the clean sample.** D11 lets the plan reviewer
see only plans that passed the deterministic checks, and most of the held-out clean e and f plans are clean as books
but carry checker ERRORs (`AL-884`). So the reviewer's clean sample is the checker-repaired baseline of each clean plan:
the same mechanical repairs the synthetic builder already makes before it seeds a defect, recorded per plan.

This directory holds:

- `<plan id>.baseline.plan.json`, one repaired plan per clean plan (indent 2, ASCII only, trailing newline);
- `manifest.json`, schema `clean-baselines/v1`: the items and a `summary`.

Generated by `scripts/build_clean_baselines.py` from committed files only (no model call, no network, no randomness).

## Which plans have a baseline

Every plan of `docs/planning/evidence/continuity-reader/validation-set.json` with `expected_verdict: "pass"` and
`label_strength: "strong"`, in either half: 12 plans.

| Half | Plans |
| --- | --- |
| Held out (10) | e1, e2, e3, e4, e5, f1, f2, f3, f4, f5 (two blind passes of each of the five fixed books) |
| Tuning (2) | `PL-the-hollow-lighthouse-postfix`, `PL-the-vanishing-orchard-postfix` |

Not included, on purpose:

- `PL-the-midnight-museum-postfix`, `PL-c1` and `PL-d3`: `pass` by ruling (`AL-882`, minor-only), but the source
  revision of those three plans is defective, and the synthetic builder refuses them as sources for the same reason;
- `PL-x3`, the weak control (`label_strength: "weak"`).

Each manifest item carries `id` (`CBL-<plan id>`), `half`, `book` (copied from the source item), `source_plan_id`,
`source_plan` and `plan` (file and sha256 each), `repairs` (the JSON pointers edited), `repair_count`, `checker_clean`,
`known_residuals` (copied from the source item), `expected_verdict: "pass"`, `scored_for: "D12"`,
`label_strength: "strong"` and `needed_repair`.

## Method

`repair_baseline` in `scripts/build_synthetic_plans.py` is reused as it stands; this builder loads that script by file
path and calls the function, so a baseline here is byte-identical to the seed source the synthetic builder starts from
(`tests/unit/test_clean_baselines.py` holds that). Starting from the source plan, the repair loops (at most 8 rounds)
until `check_plan` raises no ERROR, applying one rule per finding:

| Finding | Repair, in plain words |
| --- | --- |
| SP-2, SP-6 (a node or choice requires a fact not every route establishes) | Drop that fact from the node's or choice's `requires` list |
| SP-3 (two facts marked as contradicting each other both get established) | Drop the contradiction mark between the pair, in both directions |
| SP-9 (a denylist term, in practice the verb sense of "wound") | Reword the string from a fixed table (`SP9_REWORDINGS`), for example "when wound" becomes "when wound up" |

Any other finding has no repair and fails the build. After repair the baseline is written, then **re-read from the exact
text that goes on disk** and run through the checker again; the build fails unless that raises zero ERRORs, which is what
`checker_clean: true` records. The edits are recorded as `repairs`, a sorted list of JSON pointers. A pointer is listed
once however many facts were dropped from that list, so `repair_count` counts edited paths, not individual deletions.

The e2 rewording rows are new in `SP9_REWORDINGS`: e2 is not a seed source for the synthetic set, so it had no rows
before. The synthetic builder's output is unchanged by them (its `--check` still passes).

## Limits

- **A repaired baseline is a real plan plus mechanical edits, not a plan anyone wrote.** The repairs make the plan pass
  the checker, not read better. Dropping a fact from a `requires` list, or a contradiction mark, can remove something
  the book's author meant; the plan stays checker-clean and the book it describes is unchanged.
- **Mapmaker's Island dominates the repairs.** e3 carries 16 repaired paths and f4 carries 17, 33 of the 49. Treat a
  flag rate on those two as a flag rate on heavily edited plans.
- **Report the flag rate twice.** Once on all 12 baselines, and once on the 4 that needed no repair (e4, f1 and the two
  tuning plans) or, for held-out only, on e4 and f1 alone. A flag on a baseline that needed repair may come from the
  repair, and should be read against its `repairs` list. The held-out clean sample is still five books, never ten
  independent plans.
- **Known residuals carry over unchanged.** `known_residuals` is copied from the source item, so a reviewer flag at one
  of those minors (for example MM-5 on e2 and f5, SG-7 and SG-8 on the Signal plans, MI-12 to MI-17 on the Mapmaker's
  plans) is a true positive, as in the validation set.
- **Nothing here is merged into the real set.** The baselines are a second view of plans already in
  `validation-set.json`, which stays unchanged and labelled as it was; each baseline names its source in
  `source_plan_id`.
- **Tuning.** A prompt may be tuned on the tuning baselines only, exactly as for the validation set.

## Rebuild and check

```bash
uv run python scripts/build_clean_baselines.py            # write the baselines and the manifest
uv run python scripts/build_clean_baselines.py --check    # rebuild and compare, exit 1 on drift
uv run python scripts/build_clean_baselines.py --summary  # print the counts
uv run python scripts/build_synthetic_plans.py --check    # the seed set built from the same repairs
uv run python scripts/build_validation_set.py --check     # the set that says which plans are checker-clean
```

Exit codes: 0 ok; 1 drift, or a baseline that is not checker-clean; 2 a pinned git revision missing from the checkout.
The sources are pinned by git revision, so a shallow clone cannot rebuild; the unit tests skip there.

## Plan-only residuals (added 2026-11-22)

Checking the plan reviewer's first live findings against the fixed books showed that two tuning plans still carry
pre-fix wording that the book no longer has. They are recorded as `known_residuals` with ids starting `PO-` (plan-only)
and are not repaired, so the plans stay as written: the orchard `c_b2t_m_2` cost and `e_b2tb` gift (`PO-O2`, `PO-O3`)
and the lighthouse `e_set_stair` event (`PO-L4`). A reviewer flag at these entries is a true positive. The table is
`PLAN_ONLY_RESIDUALS` in `scripts/build_clean_baselines.py`. Evidence:
[tuning-1](../tuning-1/report.md); lesson `AL-900`.
